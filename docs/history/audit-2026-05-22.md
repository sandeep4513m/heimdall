## Audit overview

Single source of truth for the 7-pass audit. Every finding has a stable ID,
a severity, a current status, and a proposed remedy. No code is changed
during the audit phase. Fixes happen in one sweep at the end.

Severity scale:
- **A** Blocker. Build, runtime, or correctness defect. Must fix before alpha.
- **B** Significant. Hurts quality, performance, or maintainability. Should fix.
- **C** Minor. Cosmetic, dead code, or doc drift. Nice to fix.

Status: open / approved / deferred.

## Pass 1 — Build & Runtime Sanity

Methods used: fresh `cargo check`, `npm run check` (svelte-check + svelte-kit
sync), `npm run build` (vite production), grep audits across Rust + Svelte
sources, schema verification against the live `~/.heimdall/db/heimdall.db`.

`cargo clippy` was run with a dedicated `CARGO_TARGET_DIR` to avoid a cargo
cache collision between check-mode and clippy-mode artefacts. Result is
appended below once the rebuild finishes.

### P1-A1 — `vite.config.js` has a stale `@ts-expect-error` directive

**Severity:** A
**Status:** open
**Where:** `vite.config.js:4`
**Symptom:** `npm run check` exits 1 with:
> `Error: Unused '@ts-expect-error' directive.`

**Cause:** `@types/node` is now installed (visible in `package.json` devDeps),
so `process.env.TAURI_DEV_HOST` is fully typed without the directive.

**Why it's an A:** `npm run check` is the project's blessed type-check.
A failing type-check on `main` is a blocker for an alpha.

**Remedy:** Delete the `// @ts-expect-error process is a nodejs global`
comment on line 4. One line.

### P1-B1 — Stale temp files in repo root

**Severity:** B
**Status:** open
**Where:** repo root
**Files:**
- `dist_ls_tmp.txt`
- `icon_sample_tmp.txt`
- `lock_prev_tmp.txt`
- `lock_svelte_ver_tmp.txt`
- `rs_files_tmp.txt`
- `svelte_slot_warn_tmp.txt`
- `sync_output_tmp.txt`

**Symptom:** Untracked debris from past debugging sessions in the project root.

**Why it's a B:** Not tracked by git, but visible in `ls`, IDE explorer,
and the `list_directory` tool I used at session start. Dilutes the
"engineered like a kernel module" claim immediately on inspection.

**Remedy:** Delete all seven files. Add a `*_tmp.txt` rule to `.gitignore`
to prevent recurrence.

### P1-B2 — `@tauri-apps/plugin-opener` is dead npm dependency

**Severity:** B
**Status:** open
**Where:** `package.json` line 19, `package-lock.json`
**Symptom:** Listed as a runtime dep but has zero `import` statements
across all `.svelte`, `.ts`, `.js` files. The Rust side does not register
`tauri-plugin-opener` in `Cargo.toml` either. Pure dead weight.

**Why it's a B:** Adds ~50KB to `node_modules`, slows installs,
risks accidental future use of an unaudited path. Phase 0 mentioned
the swap from opener → shell; this is residue from that swap.

**Remedy:** `npm uninstall @tauri-apps/plugin-opener`.
Verify lockfile diff before commit.

### P1-B3 — `OllamaClient::default_local()` is unreachable dead code

**Severity:** B
**Status:** open
**Where:** `src-tauri/src/ollama_client.rs:55–58`
**Symptom:** Function defined, never called. Construction always goes
through `OllamaClient::new(&config.ollama_url)` in `bootstrap()`.

**Why it's a B:** Dead code in the alpha API surface. If kept, it
implies "this is a supported entry point" — it isn't.

**Remedy:** Delete the function. If a default is genuinely needed
later, make it an `impl Default` so it follows the trait conventions.

### P1-B4 — `tier_config: TierConfig` in `AppState` is stored but never read

**Severity:** B
**Status:** open
**Where:** `src-tauri/src/lib.rs:46` and `lib.rs:364`
**Symptom:** `bootstrap()` calls `build_tier_config()`, stores the result
in `AppState.tier_config`, and *no command ever reads it*. The frontend
cannot see the assigned tier, the auto-unload threshold, the chunk size,
or the rag_top_k.

**Why it's a B:** Half-implemented adaptive behavior. Today this is
silently OK because Phase 4–6 modules don't exist yet. As soon as
RAG arrives in Phase 4, the embedding model name and chunk size will
be needed by the engine — and right now there's no plumbed read path.

**Remedy:** Either (a) add a `get_tier_config` Tauri command and surface
it in the future Governor panel, or (b) remove the field from `AppState`
until Phase 4 actually consumes it. Recommendation: keep the field and
add the read command — it's two lines and unblocks Phase 4 cleanly.
Decision goes to Pass 6 (future-proofing).

### P1-B5 — Unbalanced design tokens between `tokens.ts` and `app.css`

**Severity:** B
**Status:** open
**Where:** `src/lib/tokens.ts` and `src/app.css`
**Symptom:** Both files declare the same 33 colour values. `tokens.ts`
exports them as a TS object; `app.css` declares them as CSS custom
properties. Nothing enforces that the two stay in sync. Drift is
inevitable, and the Three Laws say tokens are the single source of truth.

Today, `tokens.ts` is **only used in two places** —
`TitleBar.svelte` and `ModelSelector.svelte` (icons in the model list).
Every other component reads CSS variables directly via `var(--...)`.

**Why it's a B:** Two sources of truth for the same data, with one of
them barely used. Pure drift risk.

**Remedy:** Decide and enforce one direction. Recommendation:
- Keep CSS variables as the runtime source of truth (already true).
- Either delete `tokens.ts` entirely (the two TS uses can switch to
  inline values), or generate `tokens.ts` from `app.css` at build time
  via a tiny script. The simpler answer for an alpha is to delete it.
Decision goes to Pass 5.

### P1-C1 — Two `rgba()` literals in component styles

**Severity:** C
**Status:** open
**Where:**
- `src/lib/components/ChatPanel.svelte:1348` — `rgba(0,0,0,0.3)`
- `src/lib/components/ModelSelector.svelte:140` — `rgba(0, 0, 0, 0.4)`

**Symptom:** Both are box-shadow drop shadows. The Three Laws ban
hardcoded *hex* values explicitly, but the spirit of the rule covers
any colour literal not driven by a token.

**Remedy:** Add `--shadow-elevated: 0 1px 3px rgba(0,0,0,0.3)` and
`--shadow-popover: 0 8px 24px rgba(0,0,0,0.4)` to `app.css`. Replace
both literals with the variable. Two-token addition, two-line change.

### P1-C2 — Dual SSR + CSR vite build is wasted ~13s per build

**Severity:** C
**Status:** open
**Where:** `npm run build` output, see `audit_pass1_vite_build.txt`
**Symptom:** Vite builds an SSR bundle (`.svelte-kit/output/server/`,
~340KB across chunks including a 130KB `index.js`) **and** a client
bundle, even though `+layout.ts` sets `ssr = false` and we ship only
the client via `adapter-static`. The SSR bundle is generated, then
discarded. Total build time is roughly 27s, of which ~13s is spent on
the SSR pass that produces nothing user-facing.

**Why it's a C:** Doesn't ship anything bad — just wastes build time.
But for a project that brags about performance, the build pipeline
ought to be tight.

**Remedy:** Investigate adding `prerender = false` to `+layout.ts`
and/or a `kit.prerender.entries = []` to `svelte.config.js` so the
adapter-static prerender step skips entirely. Validate that
`cargo tauri build` still produces the right `dist/`.

## Pass 2 — Backend correctness & resource shape

Methods used: code review of `bootstrap()`, `chat_stream` command,
`OllamaClient::chat_stream` streaming loop, `db.rs` pool/query patterns,
`adaptive_config.rs` tier mapping, plus targeted greps for `unwrap`,
`expect`, `panic`, `lock()` calls, `unsafe`, `keep_alive`, capability
heuristics. Live SQLite schema verified against migration code.

### P2-A1 — Bootstrap failure produces a meaningless error to the user

**Severity:** A
**Status:** open
**Where:** `src-tauri/src/lib.rs:296–325`
**Symptom:** If `bootstrap()` fails (read-only mount, full disk, locked
DB, malformed config), `tauri::Builder::run().expect(...)` panics with
a generic message. A user launching from a `.desktop` entry sees a
window flash and disappear. There is no log file (see P2-A2),
no error dialog, no clue.

**Why it's an A:** Spec promises a serious tool. A binary that crashes
opaquely on first launch fails the spec.

**Remedy:** Wrap the `bootstrap()` await in match. On error: open a
Tauri error dialog (`tauri-plugin-dialog::message`), log the error,
exit with non-zero status. Adds ~10 LOC.

### P2-A2 — `~/.heimdall/logs/heimdall.log` is created but never written

**Severity:** A
**Status:** open
**Where:** `src-tauri/src/lib.rs:286–291` (tracing init), `adaptive_config.rs:401`
**Symptom:** Architecture spec says rotating log at `~/.heimdall/logs/heimdall.log`,
max 10MB. The log directory is created. The file is never opened, never
written, never rotated. `tracing_subscriber::fmt().init()` defaults to
stdout. App launched from `.desktop` has no stdout — diagnostics vanish.

**Why it's an A:** Bright-line spec promise broken. Without it, every
non-developer install is undebuggable.

**Remedy:** Add `tracing-appender = "0.2"` dep. Use
`tracing_appender::rolling::never(log_dir, "heimdall.log")` (we'll
implement size-based rotation later — daily rotation is acceptable
for alpha) plus a non-blocking writer. Compose with the existing
fmt subscriber. ~12 LOC, one new dep.

### P2-A3 — UTF-8 boundary bug in streaming chat

**Severity:** A
**Status:** open
**Where:** `src-tauri/src/ollama_client.rs:413–415`
**Symptom:** TCP chunks from `reqwest::Response::bytes_stream()`
arrive at network boundaries, not Unicode boundaries. `std::str::from_utf8(&chunk)`
fails on a multi-byte UTF-8 character that straddles a chunk boundary.
The whole stream aborts with `"Stream chunk is not valid UTF-8"`.

In practice: any non-ASCII conversation (Hindi, Chinese, Japanese, Korean,
Arabic, emoji like 👋) can break randomly mid-stream depending on chunk
sizes Ollama happens to send.

**Why it's an A:** The app advertises local AI for a global Linux user
base. It has to handle non-ASCII text correctly.

**Remedy:** Buffer raw bytes across chunks, then split on `\n`
(Ollama's NDJSON format guarantees newline-terminated objects).
Decode UTF-8 only on each complete line. ~15 LOC change in the
`while let Some(chunk_result)` loop.

### P2-A4 — `chat_stream` writes user message before the assistant call,
            stranding orphans on stream failure

**Severity:** A
**Status:** open
**Where:** `src-tauri/src/lib.rs:104–123` (user persist) followed by
`lib.rs:125–129` (stream call)
**Symptom:** If `state.ollama.chat_stream(...)` fails (network, OOM,
HTTP 5xx), the user message stays persisted but no assistant
response is recorded. The conversation now has a stranded user
message; on reload it shows with no reply.

**Why it's an A:** Conversation integrity. A retry creates duplicate
user messages. The user can scroll up later and find phantoms.

**Remedy:** On stream failure, persist a placeholder assistant
message: `role="assistant"`, `content="⚠️ Stream failed: <reason>"`,
`tokens_used=NULL`. The history then reads honestly. Alternative
(rejected): roll back the user message — gives no record that the
user even tried. ~6 LOC change.

### P2-B1 — `chat_stream` has no FK guard for missing conversation row

**Severity:** B
**Status:** open
**Where:** `src-tauri/src/lib.rs:92` — `chat_stream` command
**Symptom:** If frontend sends `conversation_id` for a row that doesn't
exist (race, deleted conversation, reset bug), `insert_message` fails
with FK violation, user message is lost, stream never starts.

Today the alpha frontend always creates the conversation first via
`create_conversation`, so this is a latent bug — but the API has no
server-side guarantee.

**Remedy:** Before persisting the user message, check if the
conversation row exists; if not, create it with the model name.
Three lines. Idempotent.

### P2-B2 — Tag-parser fallback can grow unbounded

**Severity:** B
**Status:** open
**Where:** `src-tauri/src/ollama_client.rs:493–...` (the inner
`while let in_think_block` loop)
**Symptom:** If a non-Ollama endpoint or a future Ollama version
emits `<think>` without ever emitting `</think>`, `tag_buf` grows
linearly with the entire response. No upper bound. Memory leak
proportional to response size.

**Why it's a B:** Only matters on the fallback path (older Ollama
or non-Ollama endpoints). Doesn't affect today's primary path.

**Remedy:** Cap `tag_buf` at, say, 1 MB. If exceeded: emit a warning
event, force-close the thinking block, and treat further content as
answer text. ~8 LOC.

### P2-B3 — `set_default_model` holds config mutex across async file IO

**Severity:** B
**Status:** open
**Where:** `src-tauri/src/lib.rs:269–276`
**Symptom:** `state.config.lock().await` is held while
`write_config().await` runs. Concurrent `get_user_preferences` waits
for fsync. No reason to serialise reads behind a write.

**Remedy:** Mutate inside the lock, clone, drop the lock, then write
the snapshot. ~3 LOC.

### P2-B4 — `tier_config` stored on `AppState` but never read

### P2-C2 — `HardwareInfo` discards the detected tier when overridden

**Severity:** C (alpha) / B (Phase 6 Governor)
**Status:** open
**Where:** `src-tauri/src/adaptive_config.rs::detect_hardware`
**Symptom:** Override replaces `tier` field; the original detected

### P2-C3 — VRAM detection skips Intel iGPUs deliberately, undocumented

**Severity:** C
**Status:** open
**Where:** `src-tauri/src/adaptive_config.rs::detect_vram_mb`
**Symptom:** Only NVIDIA (`0x10de`) and AMD (`0x1002`) sysfs vendor
IDs are checked. Intel iGPUs (`0x8086`) on cheap laptops report
`vram_mb: None` and the laptop is forced to `Tier::Minimal` if RAM
< 6GB.

**Why it's a C:** Conservative-correct (we don't promise GPU accel
we can't deliver), but the comment says "best-effort". A user with a
modern Intel laptop will be confused.

**Remedy:** Add a comment: "Intel iGPUs are not surfaced as VRAM
because Ollama cannot use them for inference (no Vulkan/CUDA path
exists in stable Ollama). Re-evaluate when Ollama gains Vulkan
support." Optionally, expose `gpu_vendor: Option<&str>` for the UI.

### P2-C4 — Capability heuristic ordering: Thinking before Vision can misclassify

**Severity:** C
**Status:** open
**Where:** `src-tauri/src/ollama_client.rs::detect_capability_from_name`
**Symptom:** A future `gemma3-vision` would match the Thinking heuristic
(via `gemma3`) before the Vision heuristic ever runs. False classification.

**Remedy:** Check Vision first, Thinking second. The
`detect_capability_from_template` upgrade path masks this for users
who actually open the model selector — but the list view stays wrong.

### P2-C5 — Capability heuristic substring matching has false-positive surface

**Severity:** C
**Status:** open
**Symptom:** `lower.contains("embed")` matches any custom name with
the word "embed" in it. Same for "vision". Heuristics on the list
view; template-based detection upgrades the truth on selection.

**Remedy:** Document the falloff in a code comment. Optionally use
word-boundary matching, but that adds regex weight for marginal gain.

### P2-C6 — No way to cancel a streaming response (Phase 4+ prerequisite)

**Severity:** C (alpha) / B (Phase 4)
**Status:** open — Pass 6 prerequisite
**Where:** spec lists `Escape` as cancel-streaming shortcut
**Symptom:** Once a stream starts, the user can only wait for the
model to finish naturally. On a 4GB box with deepseek-r1 that can be
5+ minutes.

**Remedy:** Add `tokio_util::sync::CancellationToken` to AppState
keyed by conversation_id, plus `cancel_chat_stream` command.
Real fix is invasive; defer until Phase 4. Leave a TODO comment in
`chat_stream` so the next agent doesn't miss it.

## Pass 3 — Frontend correctness & memory shape

Methods used: code review of `ChatPanel.svelte` (1404 lines), grep audits
across all Svelte files for state declarations, listener lifecycle,
scroll behaviour, image lifecycle, accessibility, font loading. Mental
RAM budget computed against spec target.

### P3-A1 — Vision images: full base64 kept in JS heap for entire conversation

**Severity:** A
**Status:** open
**Where:** `src/lib/components/ChatPanel.svelte` — `messages` state, `backendToChat`
**Symptom:** Loading a conversation with N vision messages parses each
image's base64 from the SQLite blob into a fresh `data:image/jpeg;base64,...`
string and keeps it in the `messages` reactive state for the duration
of that conversation. A 50-turn conversation with one 1024px image per
turn carries ~50 MB resident.

**Why it's an A:** Spec target is <80 MB idle and 4 GB RAM minimum.
A few vision conversations push us above the target.

**Remedy options:**
- (alpha) lazy-render: only show last 50 messages with full data,
  earlier ones as text-only stubs; expand on scroll.
- (post-alpha, structural) move images to disk:
  `~/.heimdall/images/<conv>/<msg>-<idx>.jpg`, store path in DB,
  load via `convertFileSrc` from Tauri.

**Decision:** alpha gets lazy-rendering note in DEVLOG and a hard
file-size cap (see P3-B6). Structural fix lands with Phase 4
(`input_processor` module per spec).

### P3-A2 — `scrollIntoView` per thinking token = GPU thrashing

**Severity:** A
**Status:** open
**Where:** `ChatPanel.svelte` — `unlistenThinking` handler, line 173
**Symptom:** During streaming from a thinking model, `scrollToBottom()`
fires per token. `behavior: 'smooth'` is animated (~250 ms). Animations
cancel and restart on each fire. With deepseek-r1's ~30 tokens/sec,
that's ~30 cancelled-and-restarted smooth scrolls per second. Page
lurches. CPU/GPU pegged. The model is the thing that should be using
those cycles.

**Why it's an A:** Direct violation of the "Heimdall is invisible"
principle. The app is fighting the machine while the user waits.

**Remedy:** Throttle `scrollToBottom` calls to ≤10 Hz with debounce.
Use `behavior: 'auto'` while streaming, swap to 'smooth' on done.
~10 LOC.

### P3-A3 — App fetches Google Fonts over the network on every launch

**Severity:** A
**Status:** open
**Where:** `src/app.html` lines 8–11
**Symptom:** `<link href="https://fonts.googleapis.com/css2?...">` is
fetched on every launch. Two implications:
1. **Privacy.** Google sees the cold-launch IP, User-Agent
   (WebKitGTK identifier), Accept-Language, and timing. The README
   claims "no data leaving your machine" — this is a contradiction.
2. **Functionality.** On an offline laptop the brand wordmark
   "HEIMDALL" falls back to system serif. Cinzel is the
   identity wordmark; without it, first impression is a downgrade.

**Why it's an A:** Direct spec contradiction. Heimdall's
positioning is "owned by the user, runs locally, no servers" —
shipping with a Google network call out of the box is not that.

**Remedy:** Bundle the WOFF2 files locally. Cinzel and JetBrains Mono
both have OFL — redistribution allowed. Move to `static/fonts/` and
declare via `@font-face` in `app.css`. Removes the `<link>` to
fonts.googleapis.com entirely. ~80 KB total of font assets bundled,
zero network calls. ~15 LOC change in `app.html` + `app.css`.

### P3-A4 — Streaming token race when user switches conversation mid-stream

**Severity:** A
**Status:** open
**Where:** `ChatPanel.svelte` — token handler line 138, switchConversation line 510
**Symptom:** While conversation A is still streaming, user clicks
conversation B in History. `conversationId` flips. The next streaming
token arrives with `payload.conversation_id == "A"`, current
`conversationId == "B"`. The handler silently drops the token.
`isStreaming` stays true forever in the new conversation; the spinner
never resolves. The old conversation's assistant message is persisted
correctly server-side but the user has no idea what happened.

**Why it's an A:** A live UX correctness defect. Users will think
the model is hung, hit cancel (no cancel exists yet), close the app,
file a bug.

**Remedy:** Block conversation switching while streaming. Disable
History/Models tabs during stream; show subtle "streaming…" indicator
on the chat tab. Refuse `switchConversation` calls with a toast.
Alternative (post-alpha): buffer tokens by conversation_id, merge on
switch. Alpha takes the simpler path. ~15 LOC.

### P3-B1 — `onMount` registers listeners after async init: race on early unmount

**Severity:** B
**Status:** open
**Where:** `ChatPanel.svelte::onMount` lines 124–177
**Symptom:** Listeners are registered after a sequence of `await`s.
If the component unmounts during init (user clicks Settings before
init completes), `onDestroy` fires while `unlistenToken` is still null.
The `await listen(...)` resolves on a dead component, the assignment
silently rebinds a now-unreachable variable, and the listener stays
registered for the app's lifetime.

**Remedy:** Register listeners synchronously at the top of `onMount`
(before any await), then run the heavy init. ~6 LOC reorder.

**Severity:** info
**Status:** ack
**Symptom:** Both `chat://token` and `chat://thinking` listeners are
unlisten'd in `onDestroy`. Once P3-B1 is fixed, the pattern is
leak-free.

### P3-B5 — `URL.createObjectURL(blob)` never revoked

**Severity:** B
**Status:** open
**Where:** `ChatPanel.svelte::resizeImageBlob` line 467

### P3-B6 — `pickImage` reads the entire file into memory before resize

**Severity:** B
**Status:** open
**Where:** `ChatPanel.svelte::pickImage` lines 419–425
**Symptom:** Pipeline: `readFile` (entire file → Uint8Array) →
`new Blob` (copy) → `<img>` decode (4× pixel RGBA in WebKit) →

**Remedy:**

  Resize before attaching." 5 LOC.
- (Phase 4) Move resize to Rust via `image` crate in
  `input_processor` module per spec. The pipeline becomes
  Tauri → Rust resize → base64 → JS thumbnail. WebKit never sees
  the original.

## Appendix A — Clippy run

`cargo clippy --all-targets -- -W clippy::all` could not be made to
complete in this Fedora 43 environment due to a known interaction
between Fedora's split `rust-clippy` package and `tauri-build`'s
rlib artefacts: `error[E0514]: found crate tauri_build compiled by an
incompatible version of rustc` is reported even though
`rustc --version` and `clippy --version` print identical strings.
Symptom is that `clippy-driver` carries a different `rustc-driver`
hash than `rustc`, causing `tauri_build`'s rlib to be flagged as
incompatible at link time.

Reproduced three times:
1. `cargo clippy --all-targets -- -D warnings` (after `cargo clean`).
2. `CARGO_TARGET_DIR=target_clippy cargo clippy --all-targets -- -W clippy::all`.
3. `cargo clippy --no-deps -- -W clippy::all`.

All three failed with the same E0514, with the rlib confirmed to have
been built fresh by the same `rustc 1.95.0 (59807616e 2026-04-14) (Fedora 1.95.0-5.fc43)`.

**Mitigation:** ran the equivalent rustc-native lints by inspection.
`cargo check` (default lints) returned **zero warnings on the heimdall
crate**. The audit also covers manually:
- unwrap/expect/panic surface (P1-D2),
- println/dbg surface (clean),
- dead-code identification (P1-B3, P2-B5),
- redundant-clone candidates (P1-B5 scope),
- unused/unreachable items (P1-B4 / P2-B4 — `tier_config`, `default_local`).

**Action item:** This is an environmental issue, not a code issue.
On a clean Ubuntu 22.04 / Arch box `cargo clippy` should work.
Recommend documenting this Fedora quirk in `CONTRIBUTING.md` and
adding `cargo clippy` to a CI matrix once CI is set up.
